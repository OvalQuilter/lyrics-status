LYRICS-STATUS — CHANGELOG & MODIFICATION SUMMARY
=================================================
Base Version: 3.0.7
Modified by: suici
Date: March 2026

This document summarizes all changes made to the lyrics-status project
(https://github.com/OvalQuilter/lyrics-status) from the original v3.0.7
source. All changes were applied directly to the compiled JavaScript in
dist/ and to static/panel.js. No TypeScript source files were modified.

─────────────────────────────────────────────────────────────────────
1. LOGGING
   Files: dist/StatusChanger.js, dist/PlaybackStateUpdater.js
─────────────────────────────────────────────────────────────────────
The app originally wrote to log.txt only for uncaught exceptions and
update failures. Logging was extended across both runtime classes.

PlaybackStateUpdater:
  - Logs every Spotify API poll and HTTP response code
  - Logs song detection, lyrics fetch result and source
  - Logs auth errors and token refresh events
  - Logs HTTP 204 (nothing playing)

StatusChanger:
  - Logs every Discord API send attempt with text and emoji
  - Logs HTTP response code and round-trip time
  - Logs rate limit events including retry_after duration
  - Logs how many lyric lines were merged per send
  - Removed 60fps "Song changed" log spam (~60 writes/sec)
  - Removed 60fps skip log spam when nothing is playing

─────────────────────────────────────────────────────────────────────
2. BUG FIX — Lyrics mismatch re-fetch loop
   File: dist/LyricsFetcher.js
─────────────────────────────────────────────────────────────────────
Original bug: lastFetchedFor was only set inside the live-source fetch
path, not on cache hits. This caused PlaybackStateUpdater to detect a
mismatch on every 5-second Spotify poll and redundantly re-fetch lyrics
from cache on every single tick.

Fix: lastFetchedFor is now set on the cache hit path before breaking
out of the source loop. The mismatch re-fetch block in
PlaybackStateUpdater was removed entirely as it is no longer needed.

─────────────────────────────────────────────────────────────────────
3. DISCORD RATE LIMIT HANDLING
   File: dist/StatusChanger.js
─────────────────────────────────────────────────────────────────────
The original code had no protection against Discord's custom status
rate limit (~1 update per 40 seconds under heavy use). Three
protections were added:

  Auto backoff: When Discord returns HTTP 429, the app reads
  retry_after from the response body and blocks all sends until that
  timestamp has passed. Falls back to 30s if the body cannot be
  parsed. Respects the enableBackoff setting toggle.

  Minimum send interval: A configurable minimum number of milliseconds
  enforced between any two Discord sends, checked before any other
  logic in changeStatus().

  Line merging: Consecutive lyric lines that are both already due AND
  within a configurable time window of each other are joined with a
  space into a single status update, reducing total API calls. The
  merge only considers lines whose timestamps have already been
  reached — it never pre-merges future lines.

  Song boundary protection: songChanged() now always sets _lastSentAt
  to Date.now() unconditionally so the minimum interval applies on
  the first send of every new song.

─────────────────────────────────────────────────────────────────────
4. SMART TRUNCATION
   File: dist/StatusChanger.js
─────────────────────────────────────────────────────────────────────
The original code hard-cut status text at 128 characters with
.slice(0, 128), which could break mid-word.

Replaced with smartTruncate(text, limit, lyricLines):
  - Phase 1: If multiple lyric lines were merged, drops whole lines
    from the end until the joined text fits within the limit
  - Phase 2: If a single lyric line still exceeds the limit, falls
    back to word-boundary chopping with "..." appended
  - Phase 3: If a single word exceeds the limit, hard-cuts with "..."
  - Guards against null/undefined input, returning "" safely

For advanced template mode, the template is re-rendered with
progressively fewer lyric lines until it fits, rather than chopping
the already-rendered string mid-word.

─────────────────────────────────────────────────────────────────────
5. NULL SAFETY & ERROR HANDLING
   Files: dist/StatusChanger.js, dist/PlaybackStateUpdater.js
─────────────────────────────────────────────────────────────────────
Added defensive null guards to prevent crashes from missing or
malformed Spotify metadata:

  StatusChanger:
  - applyTemplate(): songName and songAuthor default to "" if null,
    preventing .toUpperCase() crashes on missing track metadata
  - smartTruncate(): returns "" immediately if text is null/undefined
  - buildMergedLines(): anchor.text defaults to "" if undefined
  - parseStatusString(): all line.text, songName, songAuthor
    accesses null-coalesced throughout

  PlaybackStateUpdater:
  - artists[0].name guarded against empty or missing artists array,
    falls back to "Unknown"

   Files: dist/Settings.js, dist/Panel/Server.js, static/panel.js
─────────────────────────────────────────────────────────────────────
A new rateLimit block was added to settings with five fields:

  enableBackoff      (bool)   — toggles auto backoff on 429
  enableMinInterval  (bool)   — toggles the minimum send interval
  minIntervalMs      (number) — minimum ms between Discord sends
  enableMergeLines   (bool)   — toggles lyric line merging

  and on receive so the panel reads and writes it live

7. TERMINAL DISPLAY
   File: dist/index.js
─────────────────────────────────────────────────────────────────────
The original terminal display showed only song name, author, progress,
current lyric line (frozen at last Discord send), and lyrics source.

Completely rewritten with two separate intervals:

  60fps loop: runs changeStatus() and advances songProgress only.
  No rendering occurs here at all.

  1s display loop: independent setInterval that reads shared state
  and writes the display. Uses ANSI cursor positioning (ESC[H) to
  overwrite lines in place rather than console.clear(), eliminating
  the scroll-spam that occurred in Git Bash on Windows.

  Display now shows:
  - Song / Artist / Progress (MM:SS / MM:SS) / Playing or Paused
  - Lyrics source and fetch origin
  - Now: actual current lyric based on real song progress,
    independent of what was last sent to Discord
  - Next: upcoming lyric line and seconds until it fires
  - Last sent: exact text of last Discord status update
  - Send: green Ready, yellow countdown, or red RATE LIMITED
    with live seconds remaining
  - Settings: min interval, merge window, auto backoff — each
    shown as green (enabled + value) or red (Off)

13. UNICODE CODE POINT TRUNCATION FIX (March 2026)
    Files: dist/StatusChanger.js, src/StatusChanger.ts
─────────────────────────────────────────────────────────────────────
JavaScript's string.length counts UTF-16 code units, not Unicode code
points. Emoji (e.g. 🎵, 🎶) use surrogate pairs and have .length === 2
but are a single code point — which is how Discord counts toward its
128-character status limit.

This caused two bugs:
  - Lyrics containing emoji were truncated 1 character too early per
    emoji (over-truncation), wasting space in the status.
  - The phase 3 hard-cut in smartTruncate used text.slice(0, n), which
    can land inside a surrogate pair and produce a broken/garbled
    character at the end of the Discord status (visible as ? or □).
    This also affects any non-BMP Unicode characters in lyrics from
    languages such as Japanese, Korean, or Chinese that include
    characters outside the Basic Multilingual Plane.

Fix: two module-level helpers added to StatusChanger:
  cpLen(s)     — returns [...s].length  (code point count)
  cpSlice(s,n) — returns [...s].slice(0,n).join("") (safe substring)

All character-limit checks and slices in smartTruncate() and
changeStatus() now use cpLen/cpSlice instead of .length/.slice:
  - smartTruncate(): 4 length checks + 1 hard-cut slice
  - changeStatus() simple mode: prefix limit calculation,
    merged line reduction loop, and final length guard
  - changeStatus() advanced template mode: fullStatus fit check
    and per-candidate fit check in the reduction loop

Both dist/StatusChanger.js and src/StatusChanger.ts updated.

14. MERGE BUG FIX + BOM CLEANUP (March 2026)
    Files: dist/StatusChanger.js, src/StatusChanger.ts,
           dist/Settings.js, dist/index.js
─────────────────────────────────────────────────────────────────────
MERGE BUG — Root cause: buildMergedLines looked FORWARD from the
anchor line. The skip logic in changeStatus() always positions the
anchor at the LAST due line (the one where nextLine is not yet due).
By definition, nothing ahead of that anchor is yet due, so the forward
scan always found zero lines to merge. Result: every send was exactly
one line, regardless of mergeWindowMs.

Fix: buildMergedLines rewritten to look BACKWARD from the anchor.
It now collects unsent lines within mergeWindowMs behind the anchor
and returns them in chronological order (oldest first). This aligns
with the intent of the setting: "merge the last N seconds of lyrics
into one Discord status update."

  buildMergedLines signature change:
    Old: (lines, startIndex, songProgress, offset)
    New: (lines, anchorIndex, mergeWindowMs)

  mergeWindowMs is now pre-computed once per changeStatus() call
  (from Settings.rateLimit) and passed directly, removing redundant
  Settings reads inside the function.

  Previously-sent lines in the backward window are skipped (they are
  already in sentLines from an earlier send). Only fresh unsent lines
  are collected.

  The intermediate skip-logic tweak introduced during entry #13 was
  reverted back to the original clean one-liner:
    if (nextLine && nextLine.time < (songProgress + offset)) continue;
  This is correct: find the last due line, then merge backward.

EXPECTED BEHAVIOR with minInterval=6s, mergeWindow=4s:
  - Lines fire every ~3s. Each 6s interval send picks up the most
    recent ~2 lines (within the 4s window) as a merged status.
  - Lines older than 4s from the anchor are treated as stale and
    omitted — they fall outside the merge window by design.
  - The log now correctly shows "(2 line(s) merged)" on these sends.

BOM CLEANUP: dist/Settings.js and dist/index.js had a UTF-8 BOM
(EF BB BF) prefix added silently by the file-write tool. Node.js
tolerates it but it is non-standard. BOMs stripped from both files
via PowerShell byte-level rewrite. dist/StatusChanger.js confirmed
clean on this write.

17. SONG SKIP DETECTION (March 2026)
    File: dist/index.js
─────────────────────────────────────────────────────────────────────
Previous behaviour: if the user manually skipped a song mid-play,
the 60fps loop would never call songChanged() because playbackState
.ended never became true — the skip just replaced the songId.
sentLines and _lastSentAt from the old song persisted into the new
one, causing the first lyric of the new song to be skipped or
silently blocked by the stale min-interval timer.

Fix: a _lastKnownSongId variable is checked every frame. When
playbackState.songId changes and the value is non-empty, songChanged()
is called immediately, clearing sentLines and resetting _lastSentAt.
This fires before changeStatus() in the same tick so the new song's
first matching lyric is sent on the very next eligible interval.

18. RATE LIMIT BODY LOGGING IMPROVEMENT (March 2026)
    File: dist/StatusChanger.js
─────────────────────────────────────────────────────────────────────
Previous behaviour: the HTTP 429 handler called res.json() directly.
If Discord returned a non-JSON body (e.g. plain text, HTML error
page, or empty body), the .json() call would throw and the catch
branch would fall back to 30s — but the raw response body was never
logged, making it impossible to diagnose the rate limit.

Fix: handler now calls res.text() first and logs the raw body
unconditionally. JSON.parse() is then attempted on the text with a
try/catch. If parsing fails, the failure and the raw body are both
logged and the 30s fallback is applied. This makes every 429
completely observable in log.txt regardless of body format.

26. BUG FIXES — MUSIXMATCH DOUBLE-AWAIT, NETEASE MS/URL/JUNK,
    STATUSCHANGER 429 SYNC, LYRICSFETCHER REFETCH LOOP (April 2026)
    Files: dist/Sources/MusixmatchSource.js, src/Sources/MusixmatchSource.ts,
           dist/Sources/NetEaseMusicSource.js, src/Sources/NetEaseMusicSource.ts,
           src/StatusChanger.ts, src/LyricsFetcher.ts
─────────────────────────────────────────────────────────────────────
MUSIXMATCH DOUBLE-AWAIT (critical — source never worked):
  request() was wrapped in __awaiter, making it return
  Promise<Promise<Response>>. Callers yielded once, receiving the
  inner Promise instead of the Response. res.ok was always undefined
  (falsy), so every request threw "Musixmatch search HTTP undefined"
  and the source silently fell through on every song lookup.
  Additionally, MusixmatchSource.js was missing entirely from the
  running instance's dist/Sources/ — copied across.
  Fix: request() made synchronous (returns fetch() directly), matching
  the original TS intent.

NETEASE MS NORMALIZATION:
  match[4] (millisecond digits) was cast with +match[4] raw. A 2-digit
  value like "12" was treated as 12ms instead of 120ms, causing all
  NetEase lyrics to be off by ~100ms per line.
  Fix: parseInt(match[4].padEnd(3, "0")) — same fix already applied
  to MusixmatchSource in entry 15.

NETEASE URL NEWLINE:
  Template literal in getSongId() contained a literal newline +
  indentation whitespace before the closing backtick, producing a
  malformed URL. Fetch may silently succeed but the trailing whitespace
  could cause 400s or cache misses depending on the server.
  Fix: URL collapsed to a single line.

NETEASE JUNK LINE FILTER (src sync):
  dist/NetEaseMusicSource.js had filters for Chinese metadata lines
  (作词/作曲/etc.) and section labels ([Verse]/[Chorus]/etc.) but
  src/NetEaseMusicSource.ts did not. CONTEXT.md claimed the filter
  existed in parseLyrics() — now true in both files.

STATUSCHANGER 429 SYNC (src):
  src/StatusChanger.ts still used res.json() for 429 handling. Synced
  to match dist: res.text() first, raw body logged unconditionally,
  JSON.parse() attempted with try/catch, fallback to 30s on failure.

LYRICSFETCHER REFETCH LOOP (src):
  src/LyricsFetcher.ts set lastFetchedFor only inside the live-source
  try block, not on cache hits. PlaybackStateUpdater's mismatch guard
  (lastFetchedFor !== songName+artist) triggered on every 5s poll for
  cached songs, causing a redundant fetchLyrics() call each tick.
  Fix: lastFetchedFor = name + artist moved to top of fetchLyrics(),
  before cache check, matching dist/LyricsFetcher.js.
