52. BUGFIX — Status flash dnd/idle not showing; setCustomStatus reset orb (May 2026)
    Files: dist/GatewayClient.js, dist/StatusChanger.js
─────────────────────────────────────────────────────────────────────
Root cause: setCustomStatus always built the op3 status field from
gateway.presenceStatus. When a flash tick set the orb to "dnd", the next
lyric send (100ms loop) immediately overwrote it back to "online", so the
flash was invisible to observers.

  GatewayClient.js — Added _flashStatus field. flashPresence() now stores the
    current flash status in _flashStatus. setCustomStatus() uses _flashStatus
    when set, falling back to gateway.presenceStatus when not flashing. Added
    clearFlashStatus() to reset _flashStatus to null.

  StatusChanger.js — _stopFlash() now calls this._gateway.clearFlashStatus()
    after stopping the interval, so subsequent setCustomStatus calls revert
    to the base presence status.

50. FEATURE — Status flash: cycle presence orb color while playing (May 2026)
    Files: dist/GatewayClient.js, dist/StatusChanger.js, dist/Settings.js
─────────────────────────────────────────────────────────────────────
CONTEXT:
  While lyrics are playing, the Discord presence orb (online/idle/dnd) can now
  cycle through a configurable list of statuses on an interval, creating a
  flashing color effect. Designed to work with both Gateway (WS) and REST.

CHANGES:
  Settings.js — Added statusFlash block to _KEYS and defaults:
    { enabled:false, states:["online","idle","dnd"], intervalMs:500, restoreStatus:null }

  GatewayClient.js — Added _lastActivity field (cached on each setCustomStatus call).
    flashPresence(status): sends op3 with the cached activity so lyric text is
    preserved during flash ticks. Does NOT push to _presenceSentTimes (bypasses
    the 5/20s rate-limit tracker). Bug fix: previous version sent activities:[]
    which cleared the custom status text on every tick.

  StatusChanger.js — Added flash manager:
    _startFlash(): starts setInterval at max(intervalMs, 300ms), cycles states.
    _stopFlash(restorePresence): clears interval; if restorePresence=true, sends
      one final op3/REST to restore the base presence status (debounced 2s).
    _flashTick(): advances _flashIndex, calls gateway.flashPresence() or
      REST PATCH /users/@me/settings with { status } as fallback when GW is off.
    changeStatus(): calls _startFlash() when lyrics are playing, _stopFlash(true)
      when not playing or no lyrics.
    songChanged(isEnd=true): calls _stopFlash(true) to restore presence on end.

BEHAVIOR:
  - Gateway mode: flash op3s bypass the rate-limit tracker; lyric text preserved.
  - REST mode: PATCH presence status field on each tick (Discord ToS caveat noted).
  - On stop: presence is restored to statusFlash.restoreStatus or gateway.presenceStatus.
  - Disabled by default (statusFlash.enabled = false in settings.json).

    Files: dist/StatusChanger.js, src/StatusChanger.ts

47. iOS STATUS SYNC (May 2026)
    Files: dist/StatusChanger.js, dist/GatewayClient.js, dist/index.js
─────────────────────────────────────────────────────────────────────
Gateway (op 3) doesn't persist to account — iOS Discord caches its own
session state and misses op 3 updates. Two REST sync strategies added:

Per-song sync (_iOSSyncPending):
  songChanged(false) sets _iOSSyncPending={t:null,em:null} when gateway active.
  changeStatus() stamps actual statusText/emoji into it before each send.
  changeStatusRequest() fires _iOSSync() on first successful op 3 — skipped
  if op 3 rate-limited (sent=false), retries on next successful send.
  songChanged(true) clears _iOSSyncPending to prevent stale fire after restore.

Reconnect sync (_onGatewayReady):
  GatewayClient.onReady callback wired in index.js to statusChanger._onGatewayReady().
  Fires on op 0 READY; re-syncs _lastSentText via REST so iOS catches up after
  gateway reconnect (the moment iOS is most likely to be out of sync).

_iOSSync() guards:
  _captureReady, non-empty text, no restore pending (_restoreTimer),
  gateway enabled, 10s debounce (_iOSSyncSentAt) prevents double-fire
  if both triggers occur within 10s of each other.
  No-ops silently in REST-only mode.

64. FIX — GatewayClient _reset delay ignored, stuck on reconnecting (May 2026)
    File: dist/GatewayClient.js
─────────────────────────────────────────────────────────────────────
  - _reset increments _wsInstance before terminate() so the close handler
    exits early (stale instance check). Previously close handler always called
    _scheduleReconnect(5000) regardless of the delay _reset was given, and
    _reset's own _scheduleReconnect was blocked by the _reconnecting guard.
    Result: op 7 reconnected in 5s instead of 500ms; any rapid disconnect
    loop appeared stuck on "GW reconnecting" in the terminal.
  - Fix: _wsInstance++ before ws.terminate() -- _reset now controls its own
    reconnect delay (op7=500ms, op9=5s, HB miss=1s) as intended.
